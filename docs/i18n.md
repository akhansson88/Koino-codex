# Translations

KOINO ships in fifteen languages. English is the source dictionary and the
runtime fallback; every other language is generated from it and kept in sync by
a small pipeline.

## Where the text lives

- `ui/translations/en.ts` — the source of truth. Every user-facing string is a
  key here.
- `ui/translations/<language>.ts` — one typed dictionary per language. Each
  file is declared as `TranslationDictionary`, so TypeScript fails the build if
  a key is missing or renamed.
- `ui/translations/languages.ts` — the language list, native names, BCP-47
  locales and the RTL flag.
- `ui/translations/reviewed/<language>.json` — optional human-reviewed
  overrides. These always win over machine translation.
- `ui/translations/i18n-state.json` — a short hash per key recording which
  English text each translation was made from. It is what lets the pipeline
  re-translate only the strings that actually changed.
- `ui/translations/plan-library.ts` — generated copy for the built-in reading
  plans (titles and descriptions), because that content lives in
  `features/bible-plan-library.ts` rather than in the UI dictionary.
- `functions/src/push-copy.generated.ts` and
  `functions/src/emails/password-reset-copy.generated.ts` — generated copy for
  server-built notifications and the password-reset email.
- `functions/src/service-language.ts` — the shared server language list, locale
  map and fallback to English.

`ui/localization.ts` loads a dictionary the first time it is needed, so an
English user does not pay for parsing fourteen other languages at launch.
`ui/app-language.tsx` stores the choice on the device, detects the device
language on first launch, updates dates and the web `lang`/`dir` attributes,
and asks React Native to apply RTL on the next start when Arabic is selected.

## Changing copy

1. Add, change or remove the English key in `ui/translations/en.ts`.
2. Run:

   ```sh
   npm run i18n:sync
   ```

   The command compares every language with English, keeps existing reviewed
   translations, translates new or changed strings, drops removed keys and
   refreshes `i18n-state.json`. Only changed keys are sent to the translator.
3. For server copy, run `npm run i18n:sync:server` (the English source lives in
   `scripts/i18n/server-copy.mjs`). The reading-plan copy is refreshed with
   `npm run i18n:sync:plans`.
4. If a critical string needs a better translation than the machine pass, add
   it to `ui/translations/reviewed/<language>.json` and run `npm run i18n:sync`
   again. The override is preserved forever, even when the English changes.

To translate only one language while working on it:

```sh
node scripts/i18n/sync.mjs --lang=de
```

The translator protects interpolation placeholders (`{count}`, `{name}`) and
brand terms (KOINO, KJV, NKJV, the Swedish Bible names) as tokens, so a machine
translation can never break a screen by renaming a placeholder.

## Enforcement

```sh
npm run i18n:check
```

checks that every language has exactly the English keys, no empty strings, the
same placeholders, and a current source hash; it also checks the reading-plan
copy and the server push/email copy. `npm run typecheck` separately guarantees
dictionary completeness at the type level.

`.github/workflows/i18n.yml` runs the check on pull requests. On `main`, any
change to `ui/translations/en.ts`, `features/bible-plan-library.ts` or
`scripts/i18n/server-copy.mjs` triggers the sync job, which translates the delta
and commits the updated dictionaries. That is the "automatic" part: content
changes in English flow to all languages without a manual translation round.

## Adding a language

1. Add the code, native name, locale and RTL flag to
   `ui/translations/languages.ts`.
2. Add the file and export name to `languageFiles` in
   `scripts/i18n/lib.mjs`, and add its Google Translate code.
3. Add the case to `dictionaryFor` in `ui/localization.ts` (the switch is the
   registry).
4. Run `npm run i18n:sync -- --lang=<code>`.

## Server copy: notifications and email

The app writes the selected language to
`notificationPreferences/<uid>/language` whenever the member is signed in. The
Cloud Functions read it when they build:

- comment, mention and voice-prayer pushes;
- prayer-activity pushes;
- event reminders (the event title stays exactly as the host wrote it, while
  the reminder lead and start time use the member's locale);
- the branded password-reset email, including subject, preview text, HTML and
  plain-text body.

The English copy for those messages lives in `scripts/i18n/server-copy.mjs`.
`npm run i18n:sync:server` regenerates
`functions/src/push-copy.generated.ts` and
`functions/src/emails/password-reset-copy.generated.ts`; `npm run i18n:check`
also verifies them. The password-reset HTML in `email/password-reset.html` uses
`{{TOKEN}}` placeholders, so the design stays in one place and only the copy
changes per language.

Firebase's own email-verification message is still sent by Firebase, not by the
KOINO SMTP worker, so its copy is managed in the Firebase project rather than in
this repository.

## Scope

- All app screens, dialogs, actions, accessibility labels, empty states, errors
  and date/time formats are translated.
- Push notifications and the branded password-reset email are translated.
- The Bible text itself is not translated by the app: scripture stays in the
  translation the reader chose (KJV, NKJV, Reformationsbibeln 2026, SFB15), and
  book names follow that Bible version.
- User-generated content (posts, prayers, journal entries, community names) and
  community-created reading plans are never machine-translated.
